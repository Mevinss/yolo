# Архитектура

## Главный принцип

Слои общаются **только** через типы из `core/types.py` и никогда напрямую.

Это не эстетика. Из этого следуют три вещи, без которых не будет статьи:

1. **Воспроизводимость.** `core/` не знает, откуда пришёл кадр — с камеры
   или из файла. Значит записанную прогулку можно прогнать тем же кодом,
   что работал в поле, и получить те же цифры. Рецензент может повторить.

2. **Ablation.** Отключить одно слагаемое и прогнать те же записи —
   строка таблицы ablation. В поле такое невозможно: нельзя дважды пройти
   одну улицу в одинаковых условиях.

3. **Замена компонентов.** YOLOv8 → RT-DETR, добавление ультразвука,
   перенос на телефон — всё это меняет один слой, не трогая остальные.

## Поток данных за один кадр

```
Frame + Pose
     │
     ▼
┌─────────────────┐
│ perception      │  YOLO → боксы; depth → глубина; distance → метры + σ
└─────────────────┘
     │  list[Detection]
     ▼
┌─────────────────┐
│ risk            │  объекты → полярная сетка (сектор × дальность)
└─────────────────┘
     │  RiskField
     ├──────────────────────────────┐
     ▼                              ▼
┌─────────────────┐        ┌─────────────────┐
│ local_planner   │        │ routing         │  (не зависит от кадра)
│ свободный       │        │ где мы на       │
│ коридор         │        │ маршруте        │
└─────────────────┘        └─────────────────┘
     │  LocalGuidance             │  GlobalGuidance
     │  (углы КАМЕРЫ)             │  (азимуты ГЕОГРАФИЧЕСКИЕ)
     └────────────┬───────────────┘
                  ▼
        ┌─────────────────┐
        │ fusion          │  ← перевод систем координат ЗДЕСЬ
        │ argmin cost(θ)  │
        └─────────────────┘
                  │  FusionResult
                  ▼
        ┌─────────────────┐
        │ guidance        │  фраза → арбитраж → речь
        └─────────────────┘
                  │  Utterance | None
                  ▼
                Tick  ────► JSONL ────► eval/metrics.py ────► таблицы статьи
```

## Две системы координат

Источник самых неприятных ошибок в подобных системах.

| Что | Отсчёт | Где используется |
|---|---|---|
| Углы камеры | от оптической оси; − слева, + справа | `RiskField`, `LocalGuidance` |
| Географический азимут | 0 = север, по часовой | `Route`, `GlobalGuidance`, `FusionResult` |

Перевод выполняется **в одном месте** — `FusionPolicy._to_geographic()`:

```python
θ_geo = (pose.heading_deg + θ_camera) % 360
```

Ошибка здесь даёт систему, которая уверенно ведёт не туда, причём
без единого исключения в логах. Поэтому на перевод есть отдельный тест.

## Почему поле риска, а не список объектов

Планировщик мог бы работать со списком боксов напрямую. Тогда любое
изменение восприятия ломало бы планирование.

`RiskField` — абстракция «насколько опасно двигаться в сторону X
на дистанции Y». Её умеет наполнять что угодно:

* детектор объектов (есть);
* карта глубины — обрыв или стена без всякого класса (шаг 5);
* сегментация покрытия — «тротуар кончился» (задел);
* ультразвуковой датчик — низкие препятствия, которые камера теряет (задел).

Планировщик знает только про сетку. Это позволяет наращивать восприятие,
не переписывая логику движения — и прямо отвечает на требование
«хочу больше, чем YOLO».

## Разграничение «можно» и «надо»

| Слой | Отвечает на вопрос | Чего НЕ знает |
|---|---|---|
| `local_planner` | куда **можно** идти | про маршрут |
| `routing` | куда **надо** идти | про препятствия |
| `fusion` | куда идти **на самом деле** | — |

Смешение первых двух — типичная ошибка, из-за которой система
уводит человека с маршрута при каждом препятствии. Локальный
планировщик возвращает все свободные коридоры; выбор между ними
делает только `fusion`, потому что выбор зависит от маршрута.

## Локальный уровень отдаёт профиль, а не угол

`LocalGuidance` несёт **R(θ) — риск как функцию угла**, а не один
рекомендованный угол. Это не избыточность, а условие работоспособности
слияния: `argmin cost(θ)` требует знать риск для любого θ.

Что происходит, если передать один угол:

```
маршрут прямо (0°), забор занимает от −15° до +15°
свободны коридоры при −45° (широкий) и +25° (узкий)

local отдаёт −45° (самый широкий)
fusion ищет компромисс между −45° и 0° → около −25°
                                          ^^^^^ внутрь забора
```

С профилем слияние честно оценивает оба коридора и выбирает +25° —
уже, но по маршруту и свободно.

Профиль считается на сетке мельче секторов: сектор в 6.7° — это 35 см
на трёх метрах, и округление выбора до сектора теряет полезную точность.

## Самодиагностика: система обязана признавать отказ

Незрячий не может посмотреть на экран и проверить, работает ли
приложение. **Молчание системы неотличимо от «впереди чисто».**

Отсюда `SystemHealth` в каждом `Tick`. Флаги: GPS потерян или неточен,
курс ненадёжен, темно, камера встала, глубина недоступна, задержка
велика, маршрут не построен, вернуться на маршрут не удалось.

Это не диагностика для разработчика, а вход для двух слоёв:

| Слой | Что делает при деградации |
|---|---|
| `fusion` | при `HEADING_UNRELIABLE` снижает вес маршрута — вести по азимуту, не зная своего курса, значит уводить наугад; при `LOW_LIGHT` пустое поле риска перестаёт давать право на `STRAIGHT` |
| `guidance` | заменяет утверждения о мире утверждениями о системе: не «свободно», а «препятствий не вижу» |

Разница в формулировке не косметическая: первое даёт основание идти
уверенно, второе оставляет решение за человеком.

## Переход как состояние, а не как точка

Для зрячего пешеходный переход — обычная точка маршрута. Для незрячего
это самый опасный участок, и поведение системы там другое.

`FusionResult.crossing_phase`: `APPROACHING → WAITING → CROSSING → COMPLETED`.

В фазе `CROSSING` удержание курса важнее обхода мелких препятствий:
сойти с курса на проезжей части опаснее, чем задеть что-то на тротуаре.
Практически это означает временное повышение `w_route` и запрет
широких отклонений.

Фаза пишется в лог и даёт две прямые метрики: время ожидания у края
и отклонение от курса во время перехода.

## Речь как ограниченный ресурс

Незрячий ориентируется на слух. Приложение, говорящее непрерывно,
отбирает у него основной канал восприятия. **Система, предупреждающая
обо всём, опаснее системы, предупреждающей о главном.**

Поэтому `guidance/scheduler.py` — не «озвучиватель», а арбитр с бюджетом:

* не чаще одной реплики в `min_interval_s`;
* `EMERGENCY` вытесняет текущую речь и игнорирует бюджет;
* повтор с тем же `dedup_key` подавляется;
* просроченная реплика (`ttl_s`) отбрасывается, а не произносится с опозданием;
* при высокой `distance_sigma_m` вместо «в трёх метрах» — «близко».

Последний пункт принципиален: ложная точность подрывает доверие,
а доверие к аиду — это то, на что человек ставит своё здоровье.

## Формат логов

`core/serialization.py` — явные преобразователи, не `asdict()`.

Причины конкретные: `asdict()` не справляется с numpy-массивами внутри
`RiskField` и `LocalGuidance`, обратного преобразования не даёт вовсе,
и не позволяет управлять точностью чисел. Явные преобразователи дают
ещё одно свойство: при изменении контракта старая запись **падает
на отсутствующем поле**, а не читается молча с подставленным значением
по умолчанию. Для данных, на которых строятся выводы статьи, это
желаемое поведение — на них есть отдельный тест.

Что не хранится и почему:

| Что | Почему нет |
|---|---|
| Кадр | Видео пишется отдельно, `Tick.seq` служит индексом в нём |
| Время до контакта | Выводится из `distance_m` и `radial_velocity_mps`; дублирование производных даёт расхождения при пересчёте |
| Объекты в `contributors` и `cause_indices` | Хранятся индексы в `Tick.detections`, иначе каждая детекция попадает в лог дважды |

Заголовок файла содержит конфигурацию прогона и маршрут — благодаря
этому запись самодостаточна: результат воспроизводится по одному файлу.

Объём (верхняя оценка, замерена на случайных данных): **22 МБ в gzip
на получасовую прогулку при 20 к/с**, 435 МБ на двадцать прогулок.
Видео той же прогулки весит на порядок больше, поэтому логи —
не узкое место, и хранится всё.

## Конфигурация и ablation

Все настраиваемые числа — в `core/config.py`, нигде больше. Причина
не в удобстве: в статье придётся отчитаться, при каких параметрах
получены результаты. Разбросанные по коду константы делают это невозможным.

`ABLATION_PROFILES` задаёт профили, каждый из которых отключает ровно
одно слагаемое. Это готовые строки таблицы ablation:

| Профиль | Что отключено | Что должно ухудшиться |
|---|---|---|
| `no_fusion_route` | `w_route = 0` | доля дошедших маршрутов |
| `no_fusion_risk` | `w_risk = 0` | пропущенные опасности |
| `no_smoothing` | `w_smooth = 0` | противоречивые подсказки подряд |
| `no_depth` | `use_depth = False` | опасности без класса (яма, обрыв) |
| `no_scheduler` | `min_interval_s = 0` | реплик в минуту, нагрузка |

Профиль сохраняется рядом с логом прогулки: `config + запись = те же цифры`.

## Что переносится из проекта-предшественника

| Откуда (`../Проект/yolo-main/`) | Куда | Изменения |
|---|---|---|
| `models.py`, часть `blind_nav.py` | `core/perception/detector.py` | обёртка, наружу `Detection` |
| `depth_estimation.py` | `core/perception/depth.py` | + опасности без класса |
| `distance.py` | `core/perception/distance.py` | + оценка σ |
| `utils.py::compute_alert_priority` | `core/risk/scoring.py` | + категория landmark |
| `objects_translations.csv` | `data/object_profiles.csv` | + казахские названия |
| `blind_nav.py::update_heading_from_gray` | `core/io/pose.py` | + GPS и компас |
| `mobile_app/server.py` | `server/main.py` | HTTP → WebSocket, Pipeline в памяти |
| `mobile_expo/` | `app/` | + голосовой ввод цели, VoiceOver |

Перенос выполняется **без изменения поведения**, чтобы сравнение
«до/после» в статье осталось честным.

Не переносится: `panorama.py`, `search_panel.py`, `scene_memory.py` —
это поиск объекта в комнате, другая задача. Могут вернуться позже
как отдельный режим «поиск в помещении».
